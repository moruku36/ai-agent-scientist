# Contract Status

[日本語](README.ja.md)

These JSON Schemas are design contracts, not a runtime or permission engine. The CPU example is disabled and contains no executable entrypoint, real identity or connection.

An implementation must additionally enforce: unexpired actual authorization, immutable hashes and source access, accepted environment isolation, resource availability and OS-level limits, aggregate budget reservations, dataset/split rights, evaluator ownership, transition rules, cancellation and redacted export. JSON Schema alone cannot prove those properties.

The run record intentionally permits missing metrics and unchecked/inconclusive validity. A completed process must not imply valid science. Evidence hashes and measurement receipts need independent validation.

## Supplemental contracts (design only)

- [handoff.schema.json](handoff.schema.json): `harness-handoff/1`, reference-only sibling messages. [Example](../examples/handoff.synthetic.json): synthetic, deliberately expired in 2000, unresolvable symbolic IDs/zero hashes; never dispatch it.
- [evaluation-protocol.schema.json](evaluation-protocol.schema.json): `evaluation-protocol/1`, frozen estimand, exposure, conditions, runs, budgets and analysis. [Example](../examples/evaluation-protocol.synthetic.json): disabled and exploratory; symbolic hashes are not real data. Its four attempts × 300 seconds + 600 seconds evaluation/cleanup fit the illustrative 1,800-second envelope.

These supplement `design-1`; no silent migration. Runtime resolves actual hashes, enforces unique condition IDs with one baseline and at least one candidate, verifies group-disjoint splits and exposure, reconciles run counts/retries/budget, binds the issuer and receipt, and rejects expired/unauthorized execution. Arithmetic, temporal ordering, reference existence and cross-record equality are semantic checks beyond JSON Schema. Enable format checking and reject duplicate JSON keys/non-finite numbers. Load pinned local schemas only, without network `$ref` resolution. See [the handoff specification](../docs/11-harness-boundaries.md) and [protocol acceptance](../docs/12-protocol-and-acceptance.md).

## Verification contracts (additive design)

- [verification-contract.schema.json](verification-contract.schema.json), `verification-contract/1`: [inert example](../examples/verification-contract.synthetic.json). Binds the existing `design-1` plan and `evaluation-protocol/1` by immutable references, with the frozen specification, complete dependency/definition closure, evaluator, toolchain, environment, permitted replacement component interfaces, cost model and scoped claim obligations. A `formal_proof` obligation additionally requires a theorem manifest, assumptions, axiom policy and trusted verifier identity.
- [verification-report.schema.json](verification-report.schema.json), `verification-report/1`: [inert example](../examples/verification-report.synthetic.json). Binds the exact contract, candidate/configuration, run/attempt, inputs/dependencies, evaluator/toolchain/environment, issuer and issue time to evidence, outcome and scoped claims. Each passed formal claim must name its theorem, assumptions, axiom audit, proof artifact, toolchain and independent verification receipt, with the exact verification scope. Failed or inconclusive formal claims may omit `formal_evidence` when those artifacts are missing; if supplied, the complete evidence object must have the declared shape. Never invent references to make an incomplete check validate.

All new references use `{id, sha256}`. Runtime resolves them under existing access controls, verifies bytes and expected document version/type, and checks equality across the contract, plan, protocol and report. The contract's `experiment_plan` must resolve to `design-1`; `evaluation_protocol` to `evaluation-protocol/1`; report `contract` to `verification-contract/1`. A dependency closure is an immutable manifest of every transitive definition and imported dependency needed for the claim, not just a top-level import list. IDs are not fetch instructions. Hash and canonicalization rules remain those in [11](../docs/11-harness-boundaries.md); this checker does not implement JCS or artifact resolution.

`allowed_replacements` lists only candidate-owned implementation components and pinned interfaces. Its strings cannot confer write permission. The trusted admission/evaluation implementation must reject any overlap, shadowing, import resolution change or effective rewrite of trusted specification, theorem, assumptions, dependency closure, evaluator, toolchain, environment or cost model. Any legitimate trusted change requires a new reviewed contract, never a candidate rewrite. Freeze and authenticate the contract before candidate evaluation.

The cost model reference pins units, accounting boundaries, workload/input domain, measurement or formal cost semantics, correctness prerequisites and thresholds. Real elapsed time, reservations, failed attempts and verification overhead remain budgeted even when a formal model proves a narrower operation-count bound. Claim IDs must be unique, match predeclared obligations, and cover all required obligations before an overall pass. Runtime rejects missing, substituted, out-of-scope or contradictory claims and invalidates receipt reuse after any bound input changes.

A formal receipt must be issued through a trusted verification process outside candidate control. That process independently checks the pinned theorem statements and transitive definitions, audits allowed axioms/assumptions, and checks proof artifacts with the accepted toolchain. Its independence is from the candidate and writable workspace; it is not automatically independent scientific review. Missing artifacts or an untrusted issuer yield no accepted pass. A proof establishes only the formal statement under its assumptions; it cannot establish external scientific truth, novelty or empirical performance.

Synthetic report examples are constrained to `inconclusive`, with deliberately unresolvable zero hashes, no evidence and no executed run. Other shape-valid reports, including `passed`, are still untrusted claims until all semantic checks succeed. No JSON field establishes authorization or evaluator isolation. Run the [offline documentation checker](../scripts/README.md); its success is not runtime acceptance.
