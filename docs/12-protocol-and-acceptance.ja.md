## run前に計画を固定する

[評価計画schema](../schemas/evaluation-protocol.schema.json)は既存`experiment-plan.schema.json`（`design-1`）を補完し、黙って置換しない。従来のCPU例は無効の資源案であり、受付可能な完全な科学的計画ではない。実行を受入する際は非公開manifestで両文書のhashを結び付ける。旧形式は閲覧できるが、新しい計画要件を迂回して実行しない。

候補の結果を得る前に、次を固定する。

| 判断 | 必須記録 |
|---|---|
| 仮説 | 一つの反証可能な予測と、少なくとも一つの別説明 |
| 推定対象 | 主指標、方向、分析単位、集計、実用上意味のある差 |
| 分割 | 開発／最終manifestのhash、group定義、管理者、過去の接触 |
| 比較条件 | 基準／候補のsource・config hash、実際のmodel／reasoning表示、道具 |
| 反復 | 課題manifest、seed／replicate一覧、実行順、予定run数 |
| 選択 | 開発結果だけを使う選択規則。最終評価前に候補固定 |
| 失敗 | timeout／crash／出力なしの採点と、測定無効の区別 |
| 資源 | 試行上限・総予算・再試行枠・評価／cleanup予約 |
| 終了 | 予算／期限、科学的停止規則、計画逸脱の扱い |

JSON例は記号的な無効例。hashの形が合う文字列は、実在する不変artifactの証明ではない。実装側で正本を解決・照合する。計画中の`enabled=true`は自己認可にならない。

## パイロットの予算計算を解消する

従来の1run最大600秒・総計1,800秒は上限案であり、12課題・2条件・3反復が収まるという意味ではない。この比較は**再試行前でも72試行**で、各試行が上限に達すれば43,200秒に評価・cleanupが加わる。CPU設定例を72試行すべてへの許可として読まない。

実装担当は、既存枠に収まる完全な小規模計画、または別途認められた大きい枠のいずれかを固定する。受付で実run manifestから、再試行・付随処理込みの最悪予約費用を計算する。残課題を黙って省略したり、失敗を見て試行上限を変えたり、好みの結果を救うためだけに増額を求めたりしない。途中停止は未完了として実施範囲と全費用を報告する。

補完schemaの`planned_attempts`は全条件・課題・反復の初回試行数、`max_retries`は研究全体の追加試行数。均一上限なら`(planned_attempts + max_retries) × per_attempt_seconds + evaluation_cleanup_seconds <= total_worker_seconds`で受付する。異なる上限を持つrun manifestは個別予約を合計できるが、配分を実行前に固定する。worker秒は別の経過時間の期限を代替しない。

## 評価受領と科学的主張

保護した受領は`run_id`、`attempt_id`、候補／config／入力hash、計画hash、評価器hash、評価集合hash、評価時刻、妥当性、主指標またはnull、限界、発行主体を結び付ける。発行者は受入済み評価境界で確認し、候補が記した名前だけを信用しない。既存run-record schemaは要約であり、それだけではこの結び付きを証明しない。

実行成功、測定妥当、仮説支持、再現、独立レビューは別の主張。同じAI・環境での再実行は再現試行であり、独立レビューではない。プロセス完了でも有効な点数がなければ`unchecked`／`inconclusive`とし、好都合な既定値を埋めない。

論文・レポートの主張ごとに、正確な受領、反証、解析版、限界を参照する。文献主張には出典版と該当箇所も必要。自動査読点は新規性の証明や欠けた実験の代わりにならない。否定的・不確定な結果にも同じ出典を付ける。

## 統計と評価汚染

条件はtask group単位で対応付け、seed反復はtask内に位置付ける。task内で集計してからtask間の不確実性を評価する。paired bootstrapでは両条件に同じgroup再標本を使う。小標本と開発データの再利用による限界を明示し、手法・区間水準・欠測規則・副次比較を事前固定する。信頼区間は未記録の適応探索を補正しない。

全設定と探索費用を記録。インフラ測定の無効除外は事前規則に限り、予定した全対象と有効測定だけの集計を併記する。成功率のtimeoutは不成功。latencyでは成功例だけの平均ではなく、事前に決めた打切り／罰則の処理を使う。

全課題を既に設計へ使っていたら探索的解析と記載。再分割、新seed、nested CVで未接触holdoutは復活しない。最終結果から候補・記憶方針を変更したら、その集合を確認的評価から退役。開発中に繰り返す採用判定は回帰試験であり、独立した証拠が無限に得られる評価ではない。

以下はすべて**未実施**。将来の実装受入であり、今回の文書／schema検査とは区別する。

| ID | ケース | 観測すべき結果 |

| SCI-07 | 同じ課題の翻訳・派生が分割をまたぐ | group重複を拒否。確認的結果にしない |
| SCI-08 | 最終フィードバックが候補・記憶へ入る | 接触記録。追加調整前に最終集合を退役 |

| SCI-10 | 取消と正常終了が競合 | 実際の結果とcleanup保持。試行重複なし |
| SCI-11 | 新workspaceから再実行 | 決定論fixtureのartifact／指標一致、または非決定性明記 |
| SCI-12 | 私的証拠の消失・許可撤回 | 主張を検証不能と記録。公開Gitへの自動転記なし |

## 実装担当AIへの引継ぎ

README → docs/03–07 → 本書 → docs/11の順に読む。モデル実験より先にP1の記録と偽runnerの復旧を実装する。Python・OS・lock方式は実装PRで受入し、環境変数を設定しただけのものをportable sandboxと呼ばない。

作業単位ごとにschema／source版、実装した不変条件、fixture IDと実測結果、再現コマンド・環境、失敗、資源実測、移行／rollback、未解決依存を返す。日英の状態表記を維持。compile成功やモデルの自己申告だけで受入しない。

単独ループを通した後にDOTS transport、任意の記憶・CTF adapterを接続する。この設計更新は、既に許可されたrepo公開の再確認を求めない。
